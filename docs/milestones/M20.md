# M20 — Capabilities, HOP send to baseline peers, Bulletin as a FileVariant (specs 0013, 0014)

**Sizing: medium-large; three sub-steps that each land green.** This is steps
2–4 of the owner's attachment plan (`docs/questions.md` "Attachments phone
interop: DECIDED 2026-09-24 (owner, final plan)"). Step 1 (HOP receive) is
the milestone in progress in `src/` now; M20 starts after it lands.

- **M20a** capabilities (0013): codec, send, store, the `effective(P)`
  intersection, and the fallback table for non-attachment kinds.
- **M20b** HOP send to peers without Bulletin: `RichText` + `p2pMixnet` in
  the `legacy` dialect (the phones' ChaCha20-Poly1305 format).
- **M20c** Bulletin as `FileVariant.bulletin` (0014): codec, send to capable
  peers, read kind 250 and both variants; kind 250 stays readable.

## Goal

On devnet, the desktop picks the attachment rail per peer from
capabilities:

1. to a **baseline peer** (never sent `capabilities`): HOP, `legacy` dialect;
2. to a **capable peer** (every device lists variant 1): `RichText` +
   `bulletin`;
3. to a **multi-device peer with one baseline device**: HOP.

Each case is proven on the wire, and the receiver opens the file. No case
costs an extra statement. Desktop half: this repo. `pca` half: another
agent, branch `desktop/rfc-0003`.

## Steps — desktop

### M20a: capabilities (0013)

1. **Codec.** Kind 252 in `content.ts`: `Capabilities { version, kinds
   [u8; 32], fileVariants Vec<u8>, hopDialects Vec<u8>, features u32 }`;
   trailing bytes after `features` are ignored. Pin the 0013 vector
   (60 bytes) in `content.spec.ts`.
2. **Own set.** One constant built from the codec's known kinds, the
   variants this build fetches (0 after step 1; 0 and 1 after M20c), the
   dialects it decrypts (`legacy`, `aesGcm`), and feature bits 0 and 1. A
   stored hash of the last set sent per contact; a change queues a resend.
3. **Send.** Queue `capabilities` for a peer on chat accept, contact add, a
   set change, and the peer's `deviceAdded`. It rides the next outgoing
   request batch to that peer; it never triggers a submission. Diagnostics
   shows 0 extra submissions.
4. **Store.** A Dexie table `peerCapabilities` keyed by `[peer, device]`
   with the set and the message timestamp; newer replaces older;
   `deviceRemoved` deletes the row. Never a message row, never a
   notification, never in the chat list preview.
5. **Choose.** `effective(peer)` = intersection over the peer's roster, with
   the baseline set for devices with no row (0013 "The baseline set").
   Apply the fallback table: buttons as numbered text, no `tx` buttons
   without feature bit 1, `send` (kind 2) instead of `transactionReference`,
   no typing/seen/deleted to devices that lack them, no group invite. The
   Assistant and the demo bots are pca bots, so they keep the rich forms once
   pca sends its set.
6. **Tests.** Unit: intersection, baseline default, removal, timestamp order,
   each fallback row. The kind is never rendered.

### M20b: HOP send to peers without Bulletin

1. **Send path.** When `effective(peer).fileVariants` lacks 1 and `kinds`
   lacks 250: upload per base spec "HOP File Loading" in the `legacy`
   dialect (ChaCha20-Poly1305, the phones' pool-entry envelope; step 1's
   receive code and pca's `hop-client.mjs` are the references), then send
   `RichText { text: caption, attachments: [p2pMixnet { identifier,
   claimTicket, node, meta }] }`. `meta.thumbnail` holds the blurhash (UTF-8),
   as the phones do. One file per message (the phones send one).
2. **Limits.** HOP entry ≤ 2 MiB per chunk, 24 h retention, one-shot per
   ticket. The composer says "Sent over HOP; available for 24 hours" in the
   bubble's detail line for a HOP send.
3. **Ack rule** (0013 "HOP with several devices"): on receive, a device of a
   multi-device user claims and does not ack. Record in decisions.
4. **Tests.** Unit: the legacy envelope round-trips against a pca-encoded
   blob; a dialect not in `effective(peer)` is never chosen; no common
   dialect → the send is refused with the 0013 text.

### M20c: Bulletin as `FileVariant.bulletin` (0014)

1. **Codec.** `FileVariant` gains `bulletin = 1` with `BulletinFile`; pin
   vectors A (194 bytes) and B (276 bytes) of `vectors-0014.md`. A kind-250
   message and its variant-1 twin map to the same local row (the 0012 shape);
   no migration of stored rows.
2. **Send.** `effective(peer).fileVariants ∋ 1` → variant 1; else kinds ∋
   250 → kind 250; else HOP (M20b). Groups v2: variant 1 when every member
   device known lists it, else kind 250. Never a mixed `RichText`.
3. **Receive.** Kind 250, variant 0, variant 1, one bubble component.
4. **Own set.** `fileVariants = [0, 1]`.
5. **Multi-device fallback proof** (if first check 2 failed): a
   domain-level test drives the real `effective()` and send path with a
   roster of two devices (one with a row listing variant 1, one without) and
   asserts the outgoing wire is `p2pMixnet`; plus the live cases 1 and 2.
6. **e2e** `scripts/e2e-rails.mjs` → `"e2e:rails"`, headless, devnet, three
   profiles or identities:
   - **a → baseline b.** b runs with `PCD_BASELINE=1` (a test-only switch:
     no `capabilities` sent, kind 250 and variant 1 not decoded, legacy HOP
     receive on). a sends a photo. Assert on a's wire: kind 15 with
     `p2pMixnet`; b claims over HOP and the bytes match: `RAIL_HOP_OK`.
   - **a → capable c.** c sends its set with its first message; a waits for
     the row; a sends a photo. Assert kind 15 with `bulletin` on the wire; c
     fetches by CID and the bytes match: `RAIL_BULLETIN_OK`.
   - **a → c with a baseline second device.** c gains a second device
     (first check 2) that sends no set; a sends a photo; assert `p2pMixnet`:
     `RAIL_MIXED_HOP_OK`. Then the second device is removed
     (`deviceRemoved`); the next photo is `bulletin`: `RAIL_REMOVED_OK`.
   - Diagnostics: submissions per message unchanged against a run without
     capabilities (`RAIL_COST_OK`).
   - `RAILS_OK` at the end.
7. **Screenshots.** `room-hop-sent.png` (HOP detail line), both themes.

## Steps — pca (branch `desktop/rfc-0003`)

1. **Codec.** Kind 252 and `FileVariant.bulletin` in
   `bot-core/vendor/app-chat-codec.mjs`; pin the 0013 vector and
   `vectors-0014.md` A and B in `bot-core/test/codec.test.mjs`; write
   "confirmed by the pca codec" in each vectors section, or the disagreement.
2. **Send the set.** A bot sends its `capabilities` with its first reply to
   each peer and after a deploy that changes it; the set agrees with its
   0010 card bits (0013 table). Same batch as the reply: 0 extra
   submissions.
3. **Store and choose.** Per peer device, as the desktop. HOP send
   (`sendAttachment`, legacy dialect) to peers without variant 1; variant 1
   to capable peers; kind 250 only to peers that list 250 and not variant 1.
4. **Receive.** Variant 1 as kind 250 today (fetch, verify, decrypt,
   staging, media analyzer).
5. **Fallbacks.** Buttons as numbered text to peers without 242; a text
   reply "1" or the label is matched to the button.
6. **Tests.** Unit tests for the codec and the choice; the desktop's
   `e2e:rails` covers the live path with a demo bot as the capable peer if
   the desktop asks for it.

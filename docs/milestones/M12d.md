# M12d — Smooth streaming replies (owner bug, 2026-09-24)

## Goal

The owner's recording: a streaming Assistant reply paints choppily, and when
it completes the whole message "loads a second time". Both come from the
render path, not the engines. Success: a streaming reply repaints at the
display rate with no visible stalls, other bubbles do not re-render per
delta, and completion changes nothing on screen except the buttons and the
ticks appearing.

## Causes found by the reviewer (verify, then fix)

1. **Every delta re-reads and re-renders the whole room.** `writeReply`
   writes each delta batch to Dexie; `useLiveQuery(listMessages(peer))`
   re-reads every row of the room; `MessageFlow` re-renders every
   `MessageBubble`; nothing is memoized; each incoming text bubble calls
   `renderMarkdown` (marked + DOMPurify) on every render. Cost grows with
   room length: a 60-message room parses 60 markdown strings per delta.
2. **The reveal restarts at completion.** `answerArrived` returns true when
   a streaming reply completes "with text other than what streamed".
   `writeReply(id, 'received')` stores `replyContent(text)`, which strips
   the buttons block (and a CLI's closing text can replace the streamed
   text), so the text differs, the reveal starts from character 0, and the
   reply types itself again. The bubble also swaps from the
   `streamingView` branch to the normal branch, re-creating its DOM.

## Steps

1. **Stream in memory, persist on a timer.** Keep the streaming reply's
   text in a renderer store (per reply id) that the bubble subscribes to
   directly; paint on `requestAnimationFrame` (at most one paint per
   frame). Write Dexie at most every 500 ms and at the end (the stored row
   is for history, previews and restarts, not for painting). The
   "streaming reply at last close never finishes" clean-up still works.
2. **Memoize.** `MessageBubble` under `React.memo` with a stable props
   surface (callbacks from `useCallback` in Room; no fresh objects per
   render); `renderMarkdown` result under `useMemo(text)`. Prove with a
   render-count test: a delta to the streaming row re-renders one bubble.
3. **No second reveal.** At completion, if the final text starts with the
   streamed text (or equals it with the buttons block removed), do not
   start a reveal; keep the painted DOM and append only. If a CLI's closing
   text differs, reveal only the tail. Keep one DOM branch for a text bubble
   across streaming → received (the placeholder chips and the keyboard
   mount inside it), so nothing re-creates.
4. **Stalls.** Measure with the Performance API in a spec-like script or
   the CDP screenshot harness: long tasks (> 50 ms) during a streamed
   reply of ~1500 characters in a room of 60 messages must be zero after
   the change. Put the before/after numbers in `docs/acceptance.md`.
5. **Bots' live frames** (pca placeholders and edits) go through the same
   memoized path; check they still reveal once.
6. **Run**: `npm run check`, `npm run smoke`, `npm run e2e:assistant`
   (or the assistant e2e that exists), `npm run e2e:typing`.

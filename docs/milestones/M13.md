# M13 — Publish the local agent as an on-chain peer; structured directives by tool calling

## Goal

(1) **Your agent, reachable by anyone.** A Settings toggle "Publish my agent"
gives the desktop's Assistant its own on-chain identity (a username the
person picks, e.g. `shawnbot`), so a phone user or any peer can chat with
it while this app runs. It behaves like a pca bot: accepts requests, greets,
answers with the configured engine, sends bot info with a `/` menu,
buttons, seen riding the reply, one reference per transaction, and the
submission budget rules. Guard rails: who may talk to it (my contacts only /
anyone), a daily reply cap, a per-peer cooldown, and a kill switch.
(2) **Structured directives.** Engines that support tool calling (the proxy
engine first) get `send_buttons` and `propose_transaction` tools generated
from the same schema the fenced-block parser uses, so a directive arrives
as one validated object and never streams as text. The fenced block stays
the fallback for CLI engines. Wire format unchanged.

## Steps

1. **Agent identity.** Settings › Agent: "Publish my agent" with a username
   claim (the same availability check and inline `.NN` suffix as sign-up),
   registered through the identity backend as a second identity of this
   app. Store its keys separately. Show its username and a "Copy" for
   sharing. Never reuse the person's chat key.
2. **Runtime.** While the toggle is on and the app runs, the agent runtime
   runs in the main process: request/accept (respecting the allowlist),
   greet (in the Assistant's persona), reply through the configured engine
   with the Assistant's system prompt plus the operator context pca gives
   bots (buttons MUST wording), bot info with commands (`/help`, `/about`,
   `/stop`), seen riding the reply, no typing, one reference per tx, the
   identifier-retry rule for new senders. Logs to a ring buffer shown in
   Settings › Agent (last 100 events). Daily cap (default 200 replies),
   per-peer cooldown (default 5 s), kill switch (turns the toggle off and
   stops accepting).
3. **Structured directives.** For the proxy engine (OpenAI-style tool
   calls): define `send_buttons` and `propose_transaction` tools from one
   schema module shared with `parseButtonsBlock`/`toTxIntent`; a tool call
   becomes the directive object attached to the reply; the model's text is
   the message. For engines without tools, the fenced block stays. The
   Assistant room and the published agent both use it. Test: the same
   JSON through the tool path and the fenced path yields identical
   `MessageContent`.
4. **e2e.** `scripts/e2e-agent.mjs` → `"e2e:agent"`: start the app headless
   with a throwaway profile, publish its agent with a fresh username, then
   from a test identity (`pcdeceb`) request, get accepted and greeted, ask
   a question, receive the answer and a `botInfo`, press a button the agent
   offered, and check the budget: `AGENT_OK`, one submission per reply.
   `scripts/e2e-tools.mjs` → `"e2e:tools"`: the proxy engine with a fake
   OpenAI-style server that returns a `send_buttons` tool call; the room
   shows a keyboard, never JSON: `TOOLS_OK`.
5. **Screenshots**: `settings-agent.png` (toggle on, username, log),
   both themes.
6. **Run**: `npm run check`, `npm run smoke`, `npm run e2e:agent`,
   `npm run e2e:tools`, screenshots.

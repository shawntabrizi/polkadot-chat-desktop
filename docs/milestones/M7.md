# M7 — Delete for everyone (RFC-0003) and honest bot progress

## Goal

Implement chat-spec RFC-0003 message deletion in the desktop app: a sender
retracts a message, the recipient tombstones it. Show `pca` bots' live
progress as a thinking state instead of a text bubble, and reveal bot replies
with a typing animation like the phone. The `pca` half (recipient handling,
tests) is a separate task in `.refs/polkadot-chat-agents` run by another agent;
this milestone is the desktop half only, but its e2e talks to a bot that has
the `pca` half.

## Read first

- `.refs/chat-spec/rfcs/0003-message-deletion.md` — whole file. It is the spec.
  `deleted(DeletedContent { messageId }) -> 20`. Sender flow (three cases),
  recipient flow (authorization, known target, unknown target with a pending
  set, idempotence, replies and reactions), push rule, multi-device note.
- `.refs/chat-spec/base-spec.md` "Remote Message Model" and "message encoding"
  (how content kinds are SCALE-encoded; how an unknown kind must decode as
  unsupported).
- `src/renderer/domain/chat/content.ts`, `messages.ts`, `peerSession.ts`,
  `identityChannel.ts`, `manager.ts` — how content is decoded through
  `@novasamatech/host-chat` and stored. Find how the SDK encodes
  `MessageContent` and whether it can carry a kind it does not know (read
  `node_modules/@novasamatech/host-chat` and `@novasamatech/scale` sources).
- `src/renderer/ui/Room.tsx`, `MessageBubble.tsx`, `MessageFlow.tsx`,
  `MessageContextMenu` usage, `Composer.tsx`.
- `.refs/polkadot-chat-agents/bot-core/lib/live-reply.mjs` header comment:
  the placeholder is a text message `⏳ working · Ns`, edited in place with
  progress frames (`✓ …`) and finally with the answer; frames are marked
  ephemeral on the bot side only.
- `docs/reference/mobile-ux.md` (strings; Android's typing reveal for bots).
- `.refs/polkadot-design-system/SKILL.md` §10 (act then undo, no confirm).

## Steps

1. **Content kind 20.** Add `deleted` to the app's content model:
   `{ type: 'deleted', messageId: string }`. Encode and decode it with the
   same SCALE layout as the other kinds (kind byte 20, then the UUID as the
   spec encodes `messageId` elsewhere). If the SDK's encoder rejects unknown
   kinds, wrap it: encode kind 20 yourself with `scale-ts` and pass the bytes
   where the SDK takes opaque content, and decode kind 20 before handing the
   rest to the SDK. Record the approach in `docs/decisions.md`. Add a spec
   with a byte-for-byte vector you derive from the base spec's encoding rules
   (show the derivation in the spec's comment).

2. **Recipient rules** (RFC "Recipient flow"), in `messages.ts` and the
   session inbound handler:
   - apply only when the target is a message received from that peer;
   - known target: replace content with `{ type: 'deleted' }` tombstone,
     drop text, attachments, and edit history; keep `messageId` and
     timestamp; later `edited` for that id is ignored; reactions on it are
     hidden; a reply quoting it renders "Message deleted";
   - unknown target: keep a per-peer pending set in Dexie (`pendingDeletions`
     table, bounded to 500 per peer, oldest evicted) and apply on arrival;
     never display a message whose deletion was already processed;
   - idempotent.
   Specs for each rule, including deletion-before-target and duplicate.

3. **Sender flow** (RFC "Sender flow"):
   - never submitted: remove locally, send nothing;
   - otherwise: send `deleted(messageId)` through the normal send path, and
     tombstone locally at once. If the SDK exposes the outstanding request's
     queue so an unsent message can be dropped from the next statement, use
     it (case 2); if not, record in `docs/decisions.md` that pre-delivery
     removal is not available through the SDK and only the cooperative path
     is implemented.
   - UI: "Delete for everyone" in the message menu on own text messages. No
     confirm dialog. Act: the bubble becomes "Deleting…" and a Sonner toast
     "Message deleted" with Undo for 6 s; the `deleted` message is sent when
     the grace period ends; Undo restores the bubble. The toast description
     is the RFC's honest wording: "This asks their device to delete it."
   - Tombstone rendering: "Message deleted" in `text-fg-tertiary` italic,
     same bubble surface, no time/ticks besides the original time.

4. **Assistant and local rooms**: deletion of an Assistant message is local
   only (no wire); reuse the same tombstone.

5. **Bot progress as a thinking state.** In `MessageBubble`/`MessageFlow`:
   an incoming text message whose text starts with `⏳ ` (the `pca`
   placeholder) renders as the Assistant's thinking row: dimmed shimmer text
   without the hourglass, no ticks, no time; an edit of that message with
   text starting `✓ ` or any other text turns it into a normal bubble. When
   the final text arrives as an edit of the placeholder, apply the typing
   reveal (step 6). Add a spec on the classifier function (`isLiveFrame`).

6. **Typing reveal for bot replies.** Incoming text from a peer that arrives
   as an edit replacing a live frame, and the Assistant's completed replies,
   reveal at ~40 characters per 100 ms up to 2 s total, then snap to full;
   skip when the room is not visible or when `prefers-reduced-motion`.
   Never delay the data, only the paint. Setting "Reveal bot replies" in
   Settings → Chat (default on).

7. **e2e.** Extend `scripts/e2e-chat.mjs` with `--delete`: after the echo
   reply, send a message, then delete it for everyone; expect the bot (with
   the `pca` half) to answer a later `ping` without quoting the deleted text
   and to log `BOT_RECEIVED_DELETED` — the reviewer checks the bot log. Print
   `DELETE_SENT <messageId>` and `E2E_OK`.

8. **Run**: `npm run check`, `npm run smoke`, `npm run e2e:chat -- pcdpeer.47 --delete`
   (the reviewer restarts the bot on the `pca` branch before your run; if the
   bot does not log the deletion yet, say so and continue), `npm run screenshots`
   (add `room-deleted.png`: a tombstone and a live frame in one room).

## Do not

- Do not implement delete-for-me, groups, or a deletion time window (RFC
  "Unresolved Questions": out of scope, no window).
- Do not add a confirm dialog.
- Do not touch the identity or engine code.

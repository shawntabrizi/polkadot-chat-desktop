# M8 — Buttons (spec 0006): bots that feel like services

## Goal

A bot can send a message with rows of buttons; the user presses one and the
bot reacts. Desktop half: render `buttons` (kind 242), send `buttonPress`
(kind 243) or a text command, open URLs after showing the host, render unknown
actions disabled, and fall back to the numbered-list text when a peer lacks
support. The `pca` half (another agent, same branch): encode/decode both
kinds, let any AI brain emit buttons through a fenced ```buttons block in its
reply, feed presses back to the brain as a text turn, gate sending on evidence
or the operator flag. Proven by an e2e against the `pcdguide.70` bot.

## Steps

1. **Codec.** Add `buttons` and `buttonPress` to the content model and to
   `ChatMessageCodec` with the SCALE layout in the spec: `ButtonsContent {
   text: String, rows: Vec<Vec<Button>>, oneShot: bool }`, `Button { label:
   String, action: Action }`, `Action` enum `command(String)=0 |
   callback(Bytes)=1 | url(String)=2 | tx(Bytes)=3` (tx decoded as opaque
   bytes for now), `ButtonPressContent { messageId: String, row: u8, index:
   u8, payload: Bytes }`. Pin byte vectors in a spec and share them with the
   pca agent through `docs/spec/vectors-0006.md` (write the file: one
   `buttons` message with two rows, one `buttonPress`; hex plus the field
   breakdown). Both implementations must decode each other's vector.
2. **Rendering.** A `buttons` message renders `text` as a normal bubble
   (markdown allowed) and, under it inside the bubble surface, the rows as
   `Button variant="secondary" size="sm" className="rounded-medium"`; up to
   4 per row, wrapping; labels truncated at 40 chars. Unknown action kinds
   and `tx` render disabled with a tooltip "This client cannot run this
   action yet". After a press: `command` → send the string as own text
   message (shown as your bubble); `callback` → send `buttonPress`, mark the
   button pressed (spinner up to 10 s, then normal); `url` → a small inline
   confirm strip under the bubble showing the host and Open / Cancel (not a
   modal), then `shell.openExternal` through a new IPC `open:url` that only
   accepts https and polkadotapp schemes. `oneShot` keyboards collapse after
   the first press; the chat-list preview shows the `text`.
3. **Receiving `buttonPress`** (for when a person sends buttons): apply the
   spec's rule, accept only for a `messageId` we sent to that peer; store as
   a system row "<name> pressed <label>". Minimal.
4. **Compatibility.** Sending `buttons` is only for bots in practice; the
   desktop never sends it in M8. Receiving needs no gate. Record in
   `docs/decisions.md` that the desktop currently gives a bot no evidence
   except `deleted`; the pca test bots run with the operator flag.
5. **Assistant.** The local Assistant may also produce buttons: if the
   engine reply ends with a fenced ```buttons block (JSON: `{ "rows":
   [[{"label":"…","action":{"command":"…"}}]] }`), strip the block and
   render buttons; a press with `command` sends that text to the Assistant.
   Same parser the pca half uses (write it once in `src/shared/buttonsBlock.ts`
   and copy it to pca with the header comment, or the reverse; agree through
   `docs/spec/vectors-0006.md`).
6. **e2e.** `scripts/e2e-buttons.mjs` → `"e2e:buttons"`: with the e2e
   identity, request/accept with `pcdguide.70`, send `menu`; expect a
   `buttons` message (print `BUTTONS_RECEIVED rows=<n>`), press the first
   `callback` button (print `PRESS_SENT`), expect a reply text within 60 s
   that mentions the label (print `BUTTONS_OK`). If the bot answers with
   plain text instead, print `BUTTONS_FALLBACK` and exit 7.
7. **Screenshots.** `room-buttons.png` in both themes: a bot message with two
   rows of buttons, one pressed, and the URL confirm strip open.
8. **Run**: `npm run check`, `npm run smoke`, `npm run e2e:buttons`,
   `npm run screenshots`.

## Do not

- No `tx` execution, no chain calls. Decode and render disabled only.
- No modal. No auto-opening URLs.

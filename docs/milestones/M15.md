# M15 — Attachments on Bulletin (spec 0012)

**Sizing: large; about the size of M12 plus a chain integration.** The
desktop half is new in three places at once: a second chain (Bulletin
descriptors, a signer, authorization), a blob pipeline (encrypt, chunk,
store, fetch, verify), and media UI (image bubble, file row, voice recorder
and player). Plan for three sub-steps that each land green: **M15a**
Bulletin rail + codec + images (the e2e below), **M15b** files, albums,
voice notes, **M15c** re-upload on request and the quota UI. The pca half is
smaller: its HOP code already stages files for the brain. Downloading
phone-app HOP attachments (base spec `richText`) is **not** in M15; see
"Later".

## Goal

On devnet, identity a sends an encrypted image to identity b through the
Bulletin chain (para 1010); b's client fetches it by CID, verifies it,
decrypts it and shows it; the Diagnostics counter shows one statement for the
message. Then a sends an image to the bot `pcdguide.70`, and the bot replies
with a description of it. Desktop half: this repo. `pca` half (another
agent, branch `desktop/rfc-0003`).

## Steps — desktop

1. **Codec.** Kind 250 per the spec in `content.ts`; `Media`, `Store`.
   Pin vectors A and B in `content.spec.ts`; decode and re-encode byte for
   byte. Poll `vectors-0012.md` for the pca agent's confirmation (60 s, up to
   25 min); disagreement stops the step.
2. **Crypto.** `domain/chat/attachmentCrypto.ts`: chunk, nonce_i, aad_i,
   AES-256-GCM (WebCrypto), BLAKE2b-256 (the same library 0011 uses), CID
   string. Specs: C1 and C2 reproduce; swap, drop and size-change fail.
3. **Bulletin client.** `src/shared/network.ts` gains `bulletin: { endpoints,
   genesis, gateway }` per profile (devnet: `wss://bullet.sik.rocks`,
   `wss://bulletin-paseo.tservices.es:8443`, `wss://bullet.tunastaking.eu`;
   genesis `0xe101f0fa…0a59`; gateway
   `https://devnet-ipfs.api.polkadotcommunity.foundation/ipfs/`). `npx papi
   add bulletinDevnet`; commit the metadata, as M11 did. A Bulletin signer
   derived at `//allowance//bulletin//chat` from the identity seed.
   Authorization: read `account_authorization`; on devnet only, if missing,
   call `authorize_account(self, 100, 64 MiB)` signed by `//Eve` (dev key,
   devnet profile only, logged). No other profile auto-authorizes.
4. **Upload.** `domain/chat/attachments.ts`: `prepareImage` (EXIF rotate and
   strip, ≤ 2560 px, JPEG 0.8, blurhash 4×3, WebP thumbnail ≤ 2048 B when the
   3,584-byte budget allows), `upload(file) → Attachment` (budget check,
   encrypt, `store` per chunk, wait for `Stored` in a best block, retries and
   `TransactionByContentHash` check per the spec), then send kind 250 through
   the normal path. Dexie table `attachments` (messageId, index, status,
   local blob, expiresAt).
5. **Download.** `fetchAttachment(att)`: `bitswap_v1_get` → mirror → gateway,
   hash check, decrypt, length check, store locally. Auto-download images
   ≤ 5 MiB. States: loading (blurhash), ready, failed · retry, expired.
6. **UI.** Composer: a `Paperclip` button (file picker: images in M15a) and
   paste/drop of images; a preview strip with the caption field. Bubble:
   image with rounded corners, progress ring while uploading, blurhash while
   downloading, click opens a side-panel viewer (no modal). The "mobile app"
   placeholder stays only for base-spec HOP attachments. Chat-list preview
   "Photo" / caption. Diagnostics: count Bulletin transactions per session
   next to statements.
7. **e2e.** `scripts/e2e-attach.mjs` → `"e2e:attach"`: identities a and b
   (existing e2e identities). a authorizes on devnet if needed
   (`AUTH_OK`), uploads a 300 KB test PNG rendered by the script
   (`STORED <cid>` for each chunk, in a best block), sends the message
   (`SENT`, Diagnostics statements delta = 1). b receives kind 250, fetches
   by `bitswap_v1_get`, verifies the hash, decrypts, and compares SHA-256
   with the original (`FETCH_OK`). b fetches again through the gateway
   (`GATEWAY_OK`). a sends the same image to `pcdguide.70`; the bot's reply
   contains a description (a word from a fixed list the test image shows, e.g.
   "red" and "circle") (`BOT_DESCRIBE_OK`). Print `ATTACH_OK`. Exit 13 on
   timeout.
8. **Screenshots.** `attach-compose.png`, `room-image.png` (sent and received
   images, one downloading with blurhash), `attach-expired.png`, both themes.
9. **Run:** `npm run check`, `npm run smoke`, `npm run e2e:attach`,
   `npm run screenshots`.

## Steps — pca (branch `desktop/rfc-0003`)

1. **Codec.** Kind 250 in `bot-core/vendor/app-chat-codec.mjs`; pin vectors
   A, B in `bot-core/test/codec.test.mjs`; write "confirmed by pca codec" in
   `vectors-0012.md` (or the disagreement).
2. **Receive.** On kind 250: fetch (`bitswap_v1_get` on
   `BOT_BULLETIN_RPC`, then the mirror), verify, decrypt into the per-turn
   staging directory with the existing caps (32 MiB, 8 files); pass metadata
   as `toAttachmentMeta` does. Never log the key.
3. **Media understanding.** Wire the existing media analyzer into the
   Polkadot-app path behind `--media-analyzer` (today T3ams only): images and
   PDFs are described and the summary enters the prompt as untrusted data.
   Without the flag, the brain can still read the staged file.
4. **Send.** `sendAttachment` gains a 0012 path: encrypt, `store` with the
   `//allowance//bulletin//chat` key (devnet `//Eve` grant as today), send
   kind 250. HOP sending stays for phone users.
5. **Tests.** Unit tests for the crypto vectors; an e2e with the desktop's
   `e2e:attach` (the bot step).

## Do not

- No HOP download of phone-app attachments in the desktop (one-shot; see
  "Later"). No `renew`. No padding. No attachments in 0009 v1 groups beyond
  what the carrier already allows. No auto-authorization outside the devnet
  profile. No modal.

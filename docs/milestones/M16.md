# M16 — Private groups v2, core (spec 0011): one submission per message

**Sizing: this is two milestones.** M16 is the transport, keys, state,
removal, migration and a bot member. **M16b** (sketched at the end) is the
supergroup feature set: invite links, join requests, shared history, roles
and permissions UI, pins, slow mode. Level-2 privacy (per-group posting
accounts from People-chain slots) is later still and waits on the owner's
answer to 0011 Unresolved 1 and on "Sign in with Polkadot app" (M10a).

## Goal

A v2 room on devnet with two people and a bot where every group message
costs **one** statement (Diagnostics shows it), a removed member cannot read
the next message, and an existing v1 room upgrades in place. Desktop half:
this repo. `pca` half (another agent, branch `desktop/rfc-0003`): the bot is a
v2 member that replies with one statement.

## Steps — desktop

1. **Crypto and codec.** `domain/chat/groupKeys.ts`: `Topic_e`, `MsgKey_e`,
   the three channels, `WrapKey`, `hint`, seal and open with AES-256-GCM (Web
   Crypto), `K(A, B)` from the existing session key code. Codec for
   `GroupData`, `GroupMessages`, `GroupState`, `Rekey` and kind 249
   (`welcome`, `keyRequest` now; the other variants decode only). Every
   vector in `vectors-0011.md` decodes and encodes byte for byte; report any
   mismatch to the pca agent and in `docs/questions.md` instead of changing
   the vectors alone.
2. **Storage.** Dexie: `groups` gains `v: 2`, `epoch`, `state` (the decoded
   `GroupState`), `keys` (epoch → key, with erase time), `carry` (own messages
   of the last 24 h). Keep `group:<groupId>` room keys.
3. **Transport.** One subscription (`matchAny`) over every v2 group's
   current and still-kept topics, re-opened when the set changes. Send: build
   the carry (newest first, ≤ 4096 bytes plaintext, ≤ 24 h), seal, submit on
   `ChMsgs_e` with the base spec's `Expiry` rule and `ExpirationTime` = now +
   14 d; at most one submission per group per second (merge like
   `submissions.ts`). Receive: open, check signer → member → `post`, dedup by
   `messageId`, gap row once. No ACK. `manager.submit` routes v2 groups here, so
   reactions, edits, deletes and button presses work unchanged. The
   Diagnostics counter counts one group message as one message.
4. **State and removal.** Create (state on `ChState_1`, `welcome` over DM to
   each member), apply states by (epoch, version, lower signer), remove
   (`rekey` on the old topic + state on the new one), leave (`groupLeave` in
   the carry; an admin removes), timer rotation at 7 days with jitter, rekey
   fork rule, key erase after 14 days, `keyRequest` recovery. Specs for every
   rule in 0011 Testing over `createInMemoryStatementStore` (extend it with
   topics and channels if it lacks them).
5. **Migration.** An admin's v1 room shows "Upgrade to private group" in the
   members panel; it opens epoch 1 from the v1 roster (v1 admin → owner) and
   sends `welcome`s; the room keeps its rows. A receiving v2 client upgrades
   its v1 room on the `welcome`.
6. **UI (minimal).** Members panel shows role (owner/admin/member) and "Remove"
   for admins with the flag; a one-line room notice for epoch changes caused by
   a removal ("<admin> removed <member>"). No new modal; design system §10.
7. **e2e.** `scripts/e2e-group2.mjs` → `"e2e:group2"`: identities a and b
   (child processes, as `e2e-group.mjs`) and the bot `pcdguide.70`. Markers:
   `V2_CREATED` (b and the bot hold epoch 1), `ONE_SUBMISSION` (a's counter
   rises by exactly 1 for one group message), `BOT_REPLY_OK` (both receive the
   bot's reply; the bot's statement is on `Topic_1`), `CARRY_OK` (b stopped, a
   sends 3 messages, b restarts and gets all 3), `REMOVED_LOCKED_OUT` (a
   removes b with 2 submissions; b cannot open a's next carrier), `MIGRATED_OK`
   (a v1 room from M12 upgrades), then `GROUP2_OK`. `E2E_TIMEOUT <stage>` and
   exit 13 as in M12.
8. **Run**: `npm run check`, `npm run smoke`, `npm run e2e:group2`,
   `npm run e2e:group` (v1 still decodes), `npm run screenshots`
   (`room-group2.png`, `group2-members.png`, both themes).

## Steps — pca (other agent)

1. Codec for 0011 from `vectors-0011.md`; pin the vectors in
   `bot-core/test/codec.test.mjs` once both codecs agree.
2. `groups.mjs` v2: keep roster, dedup and gap rules; replace `targets`/`send`
   fan-out with one carrier submission; add epoch keys, state apply, rekey
   receive, `keyRequest`. The bot accepts a `welcome` only from an admin it
   allows (today's `admits` rule).
3. Subscribe to its groups' topics with the bot's own statement account; mind
   its allowance (one statement per group).
4. Tests in memory as the desktop's; live in `e2e:group2`.

## Do not

- No MLS, no level-2 posting accounts, no invite links or join requests (M16b),
  no history sharing (M16b), no archive server, no modal, no new dependency
  unless the adapter check in Read first proves one necessary (ask first).

## M16b (next) — supergroup features

Invite links (`InviteLink`, opener-text capability, auto-accept), `joinRequest`
/ `joinDecision` with policy 1 and 2, shared history (`history` chunks, room
notice), roles and permission flags in the members panel (owner transfer,
promote, per-flag toggles), pins (state), slow mode (sender limit and receiver
hide), name and policy edits. e2e `"e2e:group2b"`: c joins by link with
approval (`JOIN_APPROVED`), receives ≤ 100 messages (`HISTORY_OK`), a pins a
message (`PIN_OK`), slow mode holds a second message (`SLOW_OK`), `GROUP2B_OK`.
Commit: `M16b: groups v2 supergroup features (spec 0011)`.

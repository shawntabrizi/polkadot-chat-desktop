# Decisions

One bullet per choice: what, why, date.

## M0 — Electron shell (2026-09-23)

- `electron-vite` is `6.0.0-beta.1` (published 2026-04-12), not the `latest` tag `5.0.0`. 5.0.0 declares `vite ^5 || ^6 || ^7`, but the web client's `@vitejs/plugin-react@6.1.1` needs `vite ^8`. 6.0.0-beta.1 declares `vite ^6 || ^7 || ^8`, so the copied devDependencies stay at the web client's versions. The other option was electron-vite 5.0.0 + vite 7.3.6 + a downgrade of plugin-react to 5.2.0. The beta is the newest electron-vite older than three days. See docs/questions.md.
- `vite` is `8.3.0` (published 2026-09-10): the newest version older than three days inside the `^8.0.0` part of the electron-vite peer range. The web client pins 8.2.2.
- `@types/node` is `26.6.2` (published 2026-09-19): the newest version older than three days. Electron 44 ships an older Node; the newer types did not cause errors.
- `electron` `44.4.1` (published 2026-09-16) resolved as pinned. Its npm package downloads the binary on first run, not in `postinstall`.
- No pin was refused by `min-release-age=3`.
- The preload is built as CommonJS (`out/preload/index.js`). With `"type": "module"`, electron-vite emits ESM `index.mjs`, and a sandboxed preload cannot be an ES module. The main process stays ESM and uses `import.meta.dirname` for paths.
- `window.desktop` is typed as optional (`desktop?: DesktopApi`). The renderer runs without Electron in vitest, so the type makes code handle that case.
- Vitest config is a separate `vitest.config.ts`, a copy of the web client's `vite.config.ts` test block: `environment: 'node'` (the web client does not use jsdom), `fake-indexeddb` from `vitest.setup.ts`, include narrowed to `src/renderer/**/*.spec.ts(x)`.
- One `tsconfig.json` with `lib: ["ES2023", "DOM", "DOM.Iterable"]` and `types: ["node", "vite/client"]` for main, preload and renderer. The eslint `no-restricted-imports` rule, not the type config, keeps Node imports out of `src/renderer`. The other compiler options are copied from the web client.
- eslint also ignores `.agent-runs/` (git-ignored runner logs).
- The renderer shows Electron's "Insecure Content-Security-Policy" warning in dev (unpackaged) runs. The copied `index.html` has no CSP. Not changed in M0 because M0 keeps the copied code unchanged.
- `npm install` reports 8 high-severity audit findings in the dependency tree. Not addressed in M0; no dependency was changed from the plan.

## M1 — Own identity (2026-09-23)

- Dependencies, pinned: `@scure/sr25519` `2.2.0` and `@polkadot-labs/hdkd-helpers` `0.0.30` (the bot-core pins), `@scure/bip39` `2.4.0` (published 2026-08-28, the newest older than three days), dev `tsx` `4.23.15` (published 2026-09-20 07:22 UTC; npm resolved it on 2026-09-23 14:13 UTC). No pin was refused by `min-release-age=3`.
- `@novasamatech/substrate-slot-sr25519-wasm` is not added. `wallet-keys.mjs` uses it only for Coinage memo secrets; `deriveSr25519PairFromSeed` does not need it.
- `@scure/sr25519@2.2.0` is in `package.json` as the milestone asks, but no file imports it directly. `hdkd-helpers@0.0.30` brings its own nested `@scure/sr25519@1.0.0`, which is what signs. A cross-check against `.refs/bot-core/lib/register.mjs` `deriveIdentityKeys` (5 random mnemonics, run once in a scratch script, not committed) gave the same account, chat key, identifier key, lite entropy and wallet secret.
- People descriptors: copied `productsDevnetPeople.scale` and `paseoPeopleNext.scale` from `.refs/bot-core/.papi/metadata/` into `.papi/metadata/`, wrote `.papi/polkadot-api.json` with those two entries (same genesis and code hash as bot-core), and ran `npx papi generate` (papi CLI 0.22.1). It added `"@polkadot-api/descriptors": "file:.papi/descriptors"` to dependencies. The generated `dist/` is git-ignored by papi, so `"prepare": "papi generate"` rebuilds it on `npm install` (offline: it reads the committed metadata files), as bot-core does. The Bulletin descriptors are not generated (not used).
- eslint ignores `.papi/` (generated code).
- `resourcePath(name)` does not import `electron`, so the Node script can use it. Packaged = `process.versions.electron` set and `process.defaultApp` not set (what `app.isPackaged` reads). Unpackaged runs resolve `../../resources` from the module, which is the repo folder both from `src/main/resources.ts` (tsx) and from the bundled `out/main/index.js`. So `electron.vite.config.ts` needs no change in M1; M3 adds `extraResources` for the packaged app.
- `crypto.ts` keeps Node `crypto` for X25519 (as the codec does). A spec checks that the result equals `@noble/curves` x25519, which the renderer uses.
- `register.ts` ports only what the desktop flow uses: no native bandersnatch binary, no voucher, no saved or refreshed session, no `reregisterIdentity`. `searchUsernames` was ported first and then removed when the spec changed to the availability endpoint (see below).
- Availability (`identity:available`): `POST /api/v1/usernames/available?version=v1` needs a Bearer token on both backends (401 without one, checked 2026-09-23). Before sign-up there is no identity key, so the main process mints a token with a throwaway sr25519 client key (`obtainAnonymousSession`, the same challenge/token handshake as `obtainIdentitySession`; register.mjs `identityClient` does the same without a mnemonic). The token is cached per backend until it is one minute from expiry and minted again once on a 401.
- `identity:available` takes `(username, profile)`, not `(username)`: the sign-up screen has a network select, and each network has its own backend.
- `availableDigits` is 1–99 in the live answers (no 0). The digits field accepts any two digits and shows "Digits taken. Try again." for a value not in the list.
- Digits UI: a "Let the network pick" checkbox, checked by default (step 10b), and a two-digit field that is pre-filled with the first `availableDigits` entry (step 10c). The field is enabled when the box is unchecked. A value the user typed is not overwritten by a later answer.
- The button is enabled when the availability check failed (network error): the backend refuses a taken number itself, and a flaky check should not block sign-up. It is disabled while a check runs, when the name is taken, and when typed digits are not in the list.
- `createIdentity` takes the store as a parameter (`store: { save, load }`). The Electron IPC passes the safeStorage store; the Node script passes a plain-file store. It refuses to run when the store already holds an identity, so a second sign-up cannot overwrite the only copy of a mnemonic.
- `createIdentity` returns `confirmed: boolean` in addition to the three fields of step 7f. When the chain does not show the key within 180 s, the claim stands (the identity is saved) and the UI says the network has not confirmed it yet, instead of an error.
- The main-process People client waits for the finalized block and the runtime metadata before the first read, like bot-core `awaitRuntime`. It does not cache metadata on disk (bot-core does); the first read after a start can take up to a minute on the public nodes.
- `getDeviceKeys()`: when a `device.statementSeed` secret exists but the device row is missing, it rebuilds the row from the stored keys. When the seed exists and the encryption key is missing or has the wrong size, it throws instead of minting.
- `ensureSelfIdentitySeeded` also re-seeds when Dexie holds an identity row of a different account (an older phone pairing), not only when there is no row. It writes the identity's network into the `networkProfile` setting. The App uses the profile from `identity.json`.
- App start-up reads device keys only after seeding, so the first launch mints no throwaway device keys.
- Logout (Settings) clears the Dexie identity rows and runs the start-up again, which re-seeds from the saved identity. See docs/questions.md.
- The Node script (`scripts/identity-register.mjs`) loads the TypeScript sources through `tsx` (`tsImport`), not through `out/main`: `out/main/index.js` is one bundle that starts the app. It spells digits in the given name as letters (`0`→`a` … `9`→`j`) and prints a `note:` line, because the backend takes letters only and the acceptance and check names carry digits (`pcdtest1234`, `pcdrev$RANDOM`). See docs/questions.md.
- The script's plain store writes `.agent-runs/identity-<name>/identity.json` (mode 0600, folder 0700, git-ignored) with the mnemonic in plaintext, as step 11 asks.
- Vitest now also runs `src/main/**/*.spec.ts`.
- Not added: a spec for `SignUp.tsx` or for the availability parser. AGENTS.md allows new files only where a step says "add tests"; steps 3 and 9 name the two specs added. The sign-up screen was checked by hand in Electron instead (docs/acceptance.md).

## M2 — Live chat (2026-09-23)

- **Platform module.** The only browser global in `src/renderer/domain` and `src/renderer/app` was `navigator.userAgent` in `pairing/host.ts`. It now goes through `app/platform.ts` (`userAgent()`, `unknown` without a navigator). The browser result is unchanged. `crypto`, `fetch`, `WebSocket` and `TextEncoder` are Node 24 globals. Dexie gets `fake-indexeddb/auto`, which the Node runner imports before `app/database.ts`.
- **WS heartbeat.** `statementStore.ts` passed `heartbeatTimeout: Infinity` (as host-papp does). The ws provider hands it to `setTimeout`, which makes a non-finite delay 1 ms in Node and 0 ms in Chromium (WebIDL `long`). The socket was dropped as stale right after every connect, in a loop (first e2e run). It is now `2_147_483_647` ms, the largest `setTimeout` delay: the same "no heartbeat" intent. This also changes the Electron renderer, where the same loop happened.
- **Own device encryption key (self identity, step 2).** M1 seeded the identity chat key as the device encryption key. Then the device session's topics are the identity session's topics. bot-core watches that topic as its identity session, so it decrypts the multi-device key wrap with the wrong secret and drops every message (`BOT_SESSION_DECODE_FAILED`). The mobile app and bot-core use the identity account as the statement account but a separate device key. Now `deriveIdentityKeys` also returns `deviceEncryptionPrivateKey = blake2b(miniSecret, key="polkadot-chat-desktop/device-encryption", 32)`. `RendererSecrets` carries it, and `seedSelfIdentity` stores it as `device.encryptionPrivateKey` (it refuses a key equal to the chat key). It is derived, not random, so a re-seed after a wiped IndexedDB gives back the key peers know. `ensureSelfIdentitySeeded` also re-seeds a Dexie that still has the M1 layout. The statement account stays the identity account.
- Other step 2 checks: nothing in the chat path reads `peerStatementAccountId`, `peerDeviceEncPubKey` or `pairedAt`. The manager and intake use only `identityAccountId`, the chat key and the device keys. No other change was needed.
- **Identity lookup.** `lookup.ts` passed an SS58 address to host-papp's `getIdentity`. The RPC adapter runs the string through polkadot-api `AccountId().dec`, which reads hex, so every live lookup failed with "Invalid public key length". The spec used a stub repository, so it did not catch this. The GUI showed "has no chat key" for every search result, and incoming requests would have been dropped. It now passes the 0x-hex account. The spec checks the argument. host-papp reads `Consumers` at its default block (not `best`); this is SDK code. Flagged for M3 with the other identity reads.
- **Username search.** The backend retired `GET /api/v1/usernames?prefix=` (404) and now serves `GET /api/v1/usernames/search?prefix=&limit=` behind proof of compute (402), checked 2026-09-23. `search.ts` now uses the new route. On a 402 it gets a puzzle from `POST /api/v1/poc/issue`, mines it (sha256 work function and header format from `.refs/polkadot-desktop` peer/service.ts, with the backend's test vectors in the spec), and retries once. Difficulty above 24 is refused. This changes the "nothing should change" Search screen, because without it the GUI step finds nobody. The change is not caused by the self identity.
- **e2e peer resolution** reads the People chain at the best block (PLAN.md "Best block first"): `Resources.UsernameOwnerOf` → account, `Resources.Consumers` → RFC-0004 container, key type = byte 0, chat key = bytes 1..33. It uses the app's one People connection (`lazyClient.getClient()`), not `src/main/identity/directory.ts` (finalized reads; M3 changes it and it must not change in M2). It also checks that the own account has a key on chain (`SELF_NOT_ON_CHAIN`), because otherwise the peer drops the request.
- **e2e registration.** A new test identity is `<name>` + 4 random **letters**, not digits (the backend takes letters only, as in M1). It is saved under `.agent-runs/identity-<name>/`, keyed by the `--identity` name, so the next run reuses it. Registration uses M1's `createIdentity`, which still waits at the finalized head (M1 code, scheduled for M3).
- **e2e module loading.** `tsx`'s `tsImport` loads every entry in its own namespace, which would give two Dexie instances. The script calls `register()` once and uses plain `import()`.
- **e2e reply.** The spec says to accept any inbound message after the ping. An echo bot answers the empty request opener (`Echo: `) a moment after the accept, and that answer can arrive after the ping. So the script first waits up to 15 s for that greeting (`GREETING`), and only a message after that counts as `REPLY`. `REPLY_HAS_NONCE yes|no` shows whether the reply echoes the ping.
- **e2e `CONTACT_EXISTS`** is coded but does not happen in practice: Dexie is memory-only per run, so every run sends a new request (pcdpeer accepts it again).
- **Spec (step 5)**: `src/renderer/domain/chat/selfChat.spec.ts`. The self side is seeded through `seedSelfIdentity`/`readUserIdentity`/`getDeviceKeys`. The peer is built like a bot (statement account = identity account, own device key) and runs the SDK sessions over `createInMemoryStatementStore`. It covers request → accept → ping → echo, one delivery, `delivered`, and that the ping's topic is not the identity-session topic.
- `.refs/bot-core/docs/guide/testing.md` (named under "Read first") does not exist in the checkout; `test-client.mjs` and the bot-core sources were read instead.

## M3 — Persistence, restart, macOS package (2026-09-23)

- **Best-block reads (step 1).** `directory.ts` is ready at the first `bestBlocks$` emission and that block's runtime, and reads `Resources.Consumers` with `{ at: 'best' }`. The one finalized read is `isFinalized(account)`, called once after the key shows at the best block; `createIdentity` returns `finalized` next to `confirmed` and never waits for it. The sign-up notice says "Confirmed." or "Confirmed, finalizing.". `createPeopleDirectory(chain)` takes a small `DirectoryChain` (best blocks, metadata, one Consumers read, endpoint switch), so `directory.spec.ts` runs it on a fake that has no finalized-block API at all. The grep for `finalized` found no other chain wait in src/ or scripts/ (the e2e script already read at the best block).
- `waitForAttestation` polls every 3 s (was 5 s) and bounds one check with `checkMs` 40 s (was the poll interval). The directory read now has its own 15 s deadline plus one retry on the next endpoint, which a 5 s check would cut off.
- **Shared read helpers.** `src/shared/chainRead.ts` (new, browser-safe): `withTimeout` (the error carries `timeout: true`), `awaitBestRuntime`, `retryOnNextEndpoint`. The main directory, the renderer lookup and the e2e script use the same three, so all three have the same deadlines.
- **Metadata cache (step 1a).** `src/main/metadataCache.ts` (new), a copy of bot-core's `metadataCache`. Files are `<userData>/metadata/<codeHash>.bin`, not `<genesis>.bin` as the step says: polkadot-api's `getMetadata`/`setMetadata` hooks pass the runtime code hash, which is also what bot-core keys by, and a genesis key would serve old metadata after a runtime upgrade. See docs/questions.md. The folder is set once: main sets `<userData>/metadata` at `ready`; the e2e script sets `.agent-runs/metadata`. `identity:register` sets none (it loads modules with `tsImport`, one namespace per module), so it runs without a cache as before.
- **Metadata cache in the renderer.** The M2 e2e failures were in the renderer's People connection, not in `directory.ts`, so the cache is used there too. The SDK's `createLazyClient` takes a provider only, so `statementStore.ts` has a copy of it (30 lines, header comment) that passes `{ getMetadata, setMetadata }` to `createClient`. In Electron the pair is `window.desktop.chain`, two IPC channels (`chain:metadataGet`, `chain:metadataSet`) to the same main-process cache; the main side accepts only a 64-hex code hash and at most 16 MB. The Node e2e sets it with `setMetadataCache()`.
- **Endpoint fallback (step 1b).** The WS provider's `switch()` (no argument: next endpoint of the list) on a timed-out step, then the step runs once more. Only timeouts are retried, not errors. The renderer connection exposes it as `switchEndpoint()`; the chat manager already rebuilds its statement subscriptions on the reconnect.
- **Lookup at the best block (step 1c).** host-papp's `createIdentityRpcAdapter` reads `Consumers` at polkadot-api's default block (finalized) and has no option for it. `lookup.ts` now builds host-papp's repository with its own `IdentityAdapter` that reads `getValues(..., { at: 'best' })` and `watchValue(..., { at: 'best' })`, waits for the runtime once per connection, and retries once on the next endpoint. `decodeRawIdentity` and the `IdentifierKey` codec are copied from host-papp (not exported). `createIdentityLookup` now takes the connection (`lazyClient` + `switchEndpoint`), not the lazy client.
- **Restart safety (step 2).** `ensureSelfIdentitySeeded` also checks the `device.statementSeed` secret (it checked the row and two secrets). The App already ran it before the chat screens; no App change was needed.
- **Reset (step 3).** `identity:reset` deletes `identity.json` and refuses while a sign-up runs. The renderer part is `domain/identity/reset.ts` (main first, then `db.delete()`, then reload; nothing is wiped when main refuses), with `reset.spec.ts`. The "tell the renderer" of the step is the IPC answer: the renderer that asked does the wipe and the reload. Settings shows "Reset identity" behind `window.confirm` with a text that says there is no backup. The metadata cache and `window.json` stay (not identity data).
- **Test profile.** `PCD_USER_DATA_DIR` sets `userData` before `ready` (identity, IndexedDB, window state, metadata cache), so tests never open the owner's profile. `smoke-packaged.sh` always uses one (a new temp folder unless set).
- **App name and profile of the packaged app.** No `productName` in package.json, so the packaged app's name is `polkadot-chat-desktop`, as in `npm run dev`: both use `~/Library/Application Support/polkadot-chat-desktop` and the keychain entry "polkadot-chat-desktop Safe Storage". So the packaged app opens the identity `npm run dev` saved. The window and the dmg are named "Polkadot Chat" (electron-builder `productName`). See docs/questions.md.
- **electron-builder** `26.15.3` (published 2026-06-09) installed as pinned. `electron-builder.yml` is as step 4 lists. `@electron/rebuild` runs but finds nothing native to build. electron-builder adds the production `node_modules` on its own (the main bundle keeps its dependencies external); the file dependency `@polkadot-api/descriptors` is packed. The asar is 100 MB because `polkadot-api` depends on its CLI tool chain (rollup, codegen); bundling the main dependencies would cut that, not done in M3. The dmg uses the default Electron icon.
- **postinstall (step 6)** is one `node -e` check (dist folder present and not empty) `||` `node node_modules/electron/install.js`, so it works without a POSIX shell. Checked both ways: no-op with the binary present; with an empty `dist/` it downloaded and extracted Electron 44.4.1.
- **Window state (step 7)** is `src/main/windowState.ts` (new): the normal bounds are saved on `close` to `<userData>/window.json` (write then rename), and loaded at start. A saved position is used only when at least 100 px of the title bar is on a connected display; otherwise the saved size opens at the default position. Not saved in `--smoke` runs.
- New files that no step names: `src/shared/chainRead.ts`, `src/main/metadataCache.ts`, `src/main/windowState.ts`, `src/renderer/domain/identity/reset.ts`. Each holds code the steps ask for; no spec for `windowState.ts` (not asked).

### M3 review fixes (2026-09-23)

- **productName.** `package.json` has `"productName": "Polkadot Chat"`. Electron also reads it in a dev run (checked: a test app with a `productName` got `userData` `.../Polkadot Chat`). Without a guard, `npm run dev` would move to the new profile and lose the dev identity. So `src/main/index.ts` calls `app.setName('polkadot-chat-desktop')` and sets `userData` to `<appData>/polkadot-chat-desktop` when `!app.isPackaged`, before `ready`. Checked with a test app: `setName` before `ready` also names the keychain entry. Result: packaged → `~/Library/Application Support/Polkadot Chat` and "Polkadot Chat Safe Storage"; dev and `npm run smoke` → `polkadot-chat-desktop`, as before. `PCD_USER_DATA_DIR` still overrides both. This replaces the M3 entry "App name and profile of the packaged app".

## M4 — AI assistant contact (2026-09-23)

- **No new dependency.** `fetch`, `TextDecoderStream` and `AbortController` are Node and Chromium globals; `markdown-it` `15.0.1` and `dompurify` `3.4.14` were already pinned (unused until now).
- **Client (step 1).** `streamChat` also takes `baseUrl`, `key` (default `process.env.LLM_PROXY_KEY`) and `fetch` (for the spec), and resolves with the whole reply. Only `choices[0].delta.content` counts; reasoning fields and empty content are skipped. SSE lines split across reads are joined; `data: [DONE]` ends the stream; an `error` object in a chunk rejects. No temperature or reasoning options are sent. `client.ts` does not import `electron`, so the e2e script loads it with `tsx`.
- **Key in error text.** The proxy's 401 body quotes the first and last 4 characters of the key it got (seen with a wrong key). Error text reaches the renderer and Dexie (the room notice), so a 401/403 gives only "The proxy refused the API key (HTTP n)." Other error bodies are cut to 300 characters, with the key and any `…****…` token replaced.
- **Settings (step 2).** `assistant.json` is `{ version, model, baseUrl, keyEncrypted }`, written with write-then-rename, mode 0600, like `identity.json`. A stored key wins over `LLM_PROXY_KEY`; the env key is the fallback. `assistant:getSettings` returns `{ model, baseUrl, hasKey, envKey }`: `envKey` was added so the screen can say why the assistant works without a stored key. `assistant:setSettings` returns the new public settings; `key: ''` removes the stored key. The base URL must start with `http(s)://`.
- **IPC (step 3).** `assistant:send` returns `{ messageId }` (main makes the id) and streams as the step says. `assistant:error` also carries `messageId`, so the renderer knows which row broke off. One running reply per conversation: a second `send` is refused with "The assistant is still answering. Stop it first." A cancel ends with `assistant:error` "Stopped.". Main checks the input: conversation id `[\w:.-]{1,64}`, 1–64 messages, roles `system|user|assistant`, each at most 32 000 characters.
- **Peer id (step 4).** `MessageRow.peerAccountId` and `RoomRow.peerAccountId` are now `PeerId = HexString | 'local:assistant'`, and the room helpers take a `PeerId`. The Assistant is not a `ContactRow`: the chat manager reads contacts as chain peers, and a contact row needs a chat key and devices. Chats shows a fixed "Assistant" row first, with its room's preview and unread count.
- **Reply rows.** A reply is one incoming row: status `streaming` (new `MessageStatus`) from the moment `send` returns, text replaced with the latest full text on each delta (one Dexie write at a time, bursts coalesced), `received` on `done`. On `error` the partial text stays with status `failed` (an empty row is deleted), and a `system` row "Assistant: <reason>" is added, so the reason survives a restart. At start, an Assistant row still `streaming` from an earlier run is marked `failed`.
- **Context.** "Last 30 turns" = the last 30 finished text messages (user and assistant) of the room, oldest first, after the system prompt. Rows still streaming, failed replies and notices are left out.
- **Room.** `Room.tsx` takes either `manager` (contacts, unchanged) or `assistant`. In the Assistant room: no reply/react/edit buttons, Send is disabled while a reply streams, a Stop button calls `assistant:cancel`, and incoming rows render as markdown ("Thinking…" before the first text). Contact rooms do not render markdown (not asked in M4).
- **Markdown.** The "Read first" folder `src/renderer/domain/markdown/` did not exist. `src/renderer/domain/markdown/markdown.ts` is a reduced copy of `.refs/polkadot-desktop/src/shared/markdown/createMarkdown.ts`: markdown-it with raw HTML off, linkify, breaks, images as links, links with `target=_blank`; then DOMPurify. No highlight.js or KaTeX (not allowed dependencies). No stylesheet; the browser's default styles are used.
- **Links.** Main sets `setWindowOpenHandler` on the window: an `http(s)` link opens in the system browser, and no new app window opens (it would get the preload). Without it, a link in a reply would open a new Electron window.
- **Settings screen (step 5).** Model, base URL, API key (password field, cleared after Save), "Remove key", Save and Test. Test uses `askOnce` with conversation id `settings-test` and stores nothing in Dexie. The key state line says "key stored", "no key stored; the app uses the proxy key from its environment", or "no key stored". It does not name `LLM_PROXY_KEY`, because `M4.check.sh` refuses that name in `src/renderer`.
- **e2e (step 6).** `scripts/e2e-assistant.mjs` loads `src/main/assistant/client.ts` with `tsx` (as `e2e:chat` does), times out after 120 s, and matches `proxy ok` in any case. Exit 5 on a wrong reply or a failed request, 2 when `LLM_PROXY_KEY` is not set.
- New files that no step names: `src/renderer/domain/assistant/assistant.ts` (+ spec), `src/renderer/domain/markdown/markdown.ts` (+ spec). They hold the code of steps 4 and 5 and the markdown rendering of the goal.

## M5 — UI pass on the Polkadot design system (2026-09-23)

### Setup and dependencies

- **Theme bundle** copied unchanged from `.refs/polkadot-design-system/assets/theme/` to `src/renderer/theme/` (`primitives.css` is byte-identical, as `M5.check.sh` checks). `src/renderer/index.css` is `@import "tailwindcss"; @import "./theme/index.css";` as step 1b says, plus `./ui/markdown.css` and the logo rules. `theme/index.css` imports Tailwind again; the built CSS has one set of layers and one palette, so the double import costs nothing.
- **Pinned** (all older than three days, none refused by `min-release-age=3`): `tailwindcss` `4.3.3` and `@tailwindcss/vite` `4.3.3` (2026-07-16, devDependencies: build tools), `lucide-react` `1.47.0` (2026-09-17), `radix-ui` `1.6.7` (2026-07-24), `sonner` `2.0.8`, `class-variance-authority` `0.7.1`, `clsx` `2.1.1`, `tailwind-merge` `3.7.0` (2026-09-12). ## M6 — Desktop conventions and local agent engines (2026-09-23)

Leaving the room within 300 ms of a keystroke still saves. The list shows "Draft: <text>" while the draft is newer than the room's last message, in the preview's usual `text-fg-secondary`.

The RFC's Unresolved Question 6 says to take the next free index on a clash. The coordinator set 21 during the run, to match the pca side (branch `desktop/rfc-0003`). The decoded field is `targetMessageId` (the envelope has its own `messageId`). The spec pins the pca vector byte for byte: envelope id "DEL-1", timestamp 1720000000000, target "MSG-3" = `58 1444454c2d31 0030fd7790010000 00 15 144d53472d33` (the leading `58` is compact(22), the opaque-message length in a Request). My first cut used 20 and told the two apart by length. The coordinator's correction replaced it before the commit.
- **Codec approach.** The SDK's `MessageContent` enum stops at 20 and rejects any other index, so it cannot carry 21. `ChatMessageCodec` in `domain/chat/identityEvents.ts` is a `scale-ts` `createCodec` around the SDK's `ChatMessage`. On encode it writes `deleted` itself (`Struct({ messageId: str, timestamp: u64, version: u8, kind: u8, target: str })`) and gives every other kind to the SDK. On decode it reads the header first. If the version is 0 and the kind is 21, it decodes `deleted`, and it accepts it only when the target string ends the message. Any other bytes go to the SDK decoder. Both the per-device session (`peerSession.ts`) and the identity channel (`identityChannel.ts`) use it. The SDK sessions take any `Codec`, so nothing else changed. An SDK-only client fails to decode a kind-21 entry, and the independent-decode rule makes that one unsupported entry (spec'd). No new dependency.
- **Pre-delivery removal (RFC case 2) is not available through the SDK.** The `Session` API has `submitRequestMessage` and `clearOutgoingStatement()`. The latter drops the whole outgoing batch and rejects every waiter. It cannot take one message out. Only the cooperative path is implemented: every deletion of a message that may have gone out sends `deleted`. Case 1 ("never submitted") is a row in `failed`: `submitRequestMessage` rejected it, so it was never in a batch. It is removed from Dexie, and nothing is sent. A `sending` row may already be in the batch, so it takes the cooperative path.
- **Tombstone.** `MessageContent` `{ type: 'deleted' }`. The row keeps `messageId`, `timestamp`, `direction` and `status`. It loses the text, the reactions and `editedAt` (this app keeps no edit history, only the edited mark). A later `edit` does nothing (`applyEdit` changes text rows only). A later reaction is not stored. A reply that quotes the row shows "Message deleted", because the quote reads the row's own preview. A tombstone of the room's newest row makes "Message deleted" the chat-list preview.
- **Recipient rules** (`messages.ts` `applyDeletion`). The deletion is applied only to an incoming row from the same peer; own rows and other peers' rows are ignored. An unknown id goes into Dexie version 5 `pendingDeletions` (key `[peerAccountId+messageId]`, index `[peerAccountId+createdAt]`). Each peer keeps at most 500 entries, and the oldest is evicted. `addMessage` checks the set for every incoming row. A match is stored as a tombstone, does not count as unread, and removes its entry. The rules are idempotent. A deletion makes no row, so it never makes a bubble or a notification.
- **Tombstone colour on own bubbles.** Step 3 says `text-fg-tertiary`. On the inverted (own) bubble I used `text-fg-tertiary-inverted`, the same token on the inverted surface. Incoming tombstones use `text-fg-tertiary`. Both are italic.
- **Delete UI.** "Delete for everyone" (Trash icon) shows in the message menu of own text and reply rows. A failed row gets it too and is removed locally. Tombstones, rows in their Undo time and live frames take no actions. There is no confirm. The bubble shows "Deleting…". A Sonner toast "Message deleted" / "This asks their device to delete it." offers Undo for 6 s. When the time ends, `manager.deleteForEveryone` runs. The pending state is React state in `Room`, and the timer is not cleared on unmount, so closing the room still commits. If the app quits within the 6 s, nothing is sent and the message stays (docs/questions.md). With no session for the peer, `deleteForEveryone` fails before it tombstones, so the user can try again.
- **Assistant (step 4).** "Delete" (local only) on every finished text row of the Assistant room, the user's questions and the replies (not a reply that is still streaming). It uses the same tombstone and the same act-then-undo toast, without the "their device" line. It also clears the `assistant.session` setting: a CLI session would still hold the deleted text. `buildContext` already leaves out non-text rows. `writeReply` does not write over a tombstone.
- **Live frames (step 5).** `isLiveFrame` (in `content.ts`) is true for a `text` row that starts with `⏳ ` (hourglass and a space), the header that bot-core's `createProgressTracker` renders. It applies only to incoming rows in contact rooms. The row renders as a dimmed pulsing thinking row without the hourglass, with no time, no ticks, no reactions and no actions. Any edit that no longer starts with `⏳ ` makes it a normal bubble.
- **Typing reveal (step 6).** `ui/reveal.ts`: 40 characters per 100 ms, snapped to the full text at 2 s. `answerArrived` starts a reveal in three cases: a live frame replaced by other text; an Assistant reply that gets its first text after "Thinking…"; an Assistant reply that completes with text other than what streamed (CLI engines). The motion check runs when the reveal starts: `document.visibilityState === 'visible'` and not `prefers-reduced-motion: reduce`. Only the paint is cut; Dexie, Copy, quotes and the chat list have the full text. The Assistant's proxy replies stream, so they reveal from their first delta. Setting: `chat.reveal` (`on` by default), a "Reveal bot replies" switch in Settings → Chat.
- **e2e `--delete`.** After the echo reply, it sends `delete me <nonce>`, waits for the echo, calls `deleteForEveryone`, and prints `DELETE_SENT <messageId>` and `LOCAL_TOMBSTONE`. Then it sends a new `ping <nonce>` and fails if the answer quotes the deleted text. `--live-frame` (for the screenshots) sends one pca-shaped `⏳ working · …` text after the reply.
- **Screenshots.** `room-deleted.png` in both themes. The tombstone comes from the app's own menu (a `contextmenu` event on the bubble, then "Delete for everyone"). The script waits for "Deleting…" and the toast text, then for the tombstone. The live frame is a real message from the `PCD_SCREENSHOT_ROOM_WITH` identity (`--live-frame`). The echo bot `pcdpeer.47` sends no live frames, so without `PCD_SCREENSHOT_ROOM_WITH` the shot is reported missing. `MessageBubble` got `data-testid="bubble"` for this.
- **New files no step names**: `src/renderer/ui/reveal.ts` (+ `reveal.spec.ts`).
- **No new dependency.**

## M7b — Unified search (contacts, global, messages) (2026-09-23)

- **Files.** `ui/searchSections.ts` (+ spec) holds the pure rules: chat matching, the three-letter rule, section assembly with the global de-duplication, the one keyboard order, `moveHighlight`, and the message snippet. `SearchPane` in `ui/Search.tsx` is the field plus the results view; it replaces `NewChatPanel`, which is removed. The draft room stays. `ChatList` no longer filters: it exports `useChatRows` (the list's rows, which the search filters) and `useChatOrder()` (⌘↑/⌘↓/⌘1…9 always use the full list). `src/main/headless.ts` is new (see below).
- **Chats and contacts section.** Case-insensitive substring on the row name (username; the Assistant row is "Assistant"). It uses the chat list's own rows, so it also shows the pending requests this user sent (they are chat-list rows); without that, filtering would lose them compared with M6. A global hit whose account is any of these rows is dropped.
- **Global search.** 400 ms after the last keystroke and from 3 characters (trimmed, lower case). `searchUsernames` now takes `{ limit, cursor }` and returns `{ results, nextCursor }`. The page size is 8 (`limit=8`), and "Show more" fetches the next page with the backend's `nextCursor` (checked live: `pcd` gave 7 rows, then 14). While a search is pending the section shows "Searching…". On an error it shows a quiet "Search unavailable" (tertiary, no alert role). A failed "Show more" keeps the rows and hides the button. Each search has a 15 s limit that also stops the proof-of-work mining. Reason: in one screenshot run searches stayed at "Searching…" for more than 60 s. The likely cause was timer throttling of the backgrounded window during mining (fixed by the headless mode below). The limit makes sure the screen always ends in a state.
- **Messages section.** `searchMessages` in `domain/chat/messages.ts`: `text` and `richText` rows only, as step 1c says (so `reply` rows are not searched, docs/questions.md). It skips a bot's live frame (status, not content). The match is a case-insensitive substring. It returns the newest first, at most 20. Own hits start with "You: ". The snippet keeps 24 characters before the match and shows the match in `font-semibold text-fg-primary`.
- **Step 4 index choice: no index, no schema change.** It reads the whole table with `toArray()` and filters in JavaScript. Measured in the spec with 5 000 rows: 10.0 ms (budget 50 ms). The first cut used Dexie `Collection.filter()` (a cursor per row) and took 89.1 ms in fake-indexeddb, so it was replaced. A `text` index would not help a substring match anyway.
- **Keyboard.** Nothing is highlighted at first. ↓ takes the first row and ↑ the last; both stop at the ends. When the highlighted row goes away, ↓ starts from the top again. Enter opens the highlighted row only. Esc in the field clears the search and leaves "+". When the search is already empty, Esc goes to the window (close the room), as before. The highlight uses the row hover colour (`bg-selection-container-hover`), and selection keeps `-active`. ⌘K focuses the search; ⌘N is "+". The Settings → Keyboard list shows both and the search keys.
- **"+".** It focuses the same field with the placeholder "Type username"; otherwise the placeholder is "Search by username or in messages" (mobile strings). With the field empty it shows "Recent": up to 5 contact rooms (no Assistant, no pending requests), in chat-list order (last message). With none it shows "Type a username to find someone." The + button shows as active while in this state.
- **After a pick.** The results stay until Esc, as in Telegram Desktop, so the user can open several hits. Exceptions: a pick from Recent (empty field) goes back to the list, and a sent request clears the search so the new pending row is visible.
- **Jump to a message.** `Selection` `room` has `jump: { messageId, seq }`. `Room` takes `scrollToMessageId` and `scrollRequest` (the seq lets the same hit jump again). `MessageFlow` scrolls the row to the centre after the first placement and highlights it for 1.5 s. The highlight is a band behind the row (`-mx-2 px-2 rounded-nested bg-selection-container-active`), not the bubble's own background. On the inverted own bubble that token would put light text on a light fill. The band has no vertical padding, because padding stopped the bubble's margin from collapsing and moved every row by 4 px (seen in a screenshot, then reverted).
- **M7 review carry items.** `isLiveFrame` accepts `⏳ ` and `🤔 ` (pca's first placeholder "🤔 One moment — thinking…"); `liveFrameText` drops either. The chat list shows "Typing…" in `text-fg-tertiary` for a room whose newest row is an incoming live frame (a newer draft still wins). `ChatRow` got `previewTone`, `highlighted`, and a `ReactNode` preview (for the bold match).
- **Screenshots.** `search.png` uses the query `pcdp`. The first time, the script sends a request to the pirate bot `pcdpirate.81` through a global hit and the draft room; that is a live check of step 1b. It also sends one message that names the bot in the room peer's room.
